오늘 배운 핵심 개념 (C#과 비교하며 이해한 원리)

  • 익명 클래스 vs 람다: 과거 자바는 함수를 파라미터로 넘기기 위해 일회용 클래스(익명 클래스, new Function<T, R>() { ... })를 매번 힙 메모리에 인스턴스화해야 했으나, 자바 8 람다(->)는 불필요한 클래스 껍데기를 모두 걷어내고 핵심 실행 로직만 간결하게 전달함.
  • this와 스코프의 비밀 (Foo.this.x vs this.x): 익명 클래스는 독립된 별도 클래스(Foo$1)로 컴파일되어 this가 익명 클래스 자신을 가리키므로 외부 클래스 멤버 접근 시 Foo.this.x라는 문법이 강제되었음. 반면 람다는 컴파일러가 원본 클래스의 private 합성(Synthetic) 메서드로 변환(어휘적 스코프)하므로 람다 내부의 this가 곧 원본 클래스 자신을 가리킴(Foo.this == this).
  • final과 변수 캡처의 원리: C#은 람다가 바깥 지역 변수를 쓸 때 힙(클로저 객체)으로 변수를 승격시켜 값 변경이 자유롭지만, Java는 스택 변수 값을 복사해 오므로 람다 내부와 외부의 값 불일치를 방지하기 위해 캡처 대상이 반드시 final(또는 값이 안 바뀌는 유사 파이널)이어야 함.
  • 인스턴스화와 최적화: 익명 클래스는 호출마다 new로 힙에 인스턴스를 만들어 GC(Garbage Collector) 부담이 크지만, 람다는 JVM의 invokedynamic 바이트코드 명령어로 가볍게 처리되고 정적 캐싱됨.

비교 코드 실습 (Function<String, String> addSurname)

Java · 익명 클래스 (람다 X)
Function<String, String> addSurname = new Function<String, String>() {
    @Override
    public String apply(String name) {
        return name + " Kim";
    }
};
Java · 모던 람다 (람다 O)
Function<String, String> addSurname = name -> name + " Kim";
깨달음: 개발자가 작성하는 건 화살표(->) 하나지만, 그 뒤에서 컴파일러가 엄청난 양의 추상화와 JVM invokedynamic 최적화를 대신 수행해주고 있음을 확인!

핵심 개념 & 깨달음 (Takeaways)

  • 람다의 다이어트 공식: 구형 익명 클래스에서 생성 문법, 어노테이션, 메서드 상세 정보를 싹 다 가위질하고 (인자 목록) -> { 실행 몸통 }만 남긴 결과물.
  • 콜백(Callback)의 진짜 주체와 흐름:
    • sort가 끝나고 메인으로 돌아가는 건 단순한 '리턴(Return)'임.
    • 진짜 콜백은 정렬 알고리즘이 두 요소를 비교해야 할 때마다 우리가 넘겨준 람다(심판)를 역으로 호출(Call-back)하는 것임 (동기 콜백 / 전략 패턴).
  • C# 이벤트 +=의 정체 (구독자 수첩): +=는 앞사람을 덮어쓰지 않고 '구독자 명단 수첩에 내 함수를 추가(Add)'하는 구조 (Java의 addActionListener와 100% 동일한 원리).
내 프로젝트(『내 약국에는 정상이 없다』) 아키텍처와의 비교 및 재발견

『내 약국에는 정상이 없다』의 GameManager 오케스트레이션은 람다 콜백 큐와 동작 목적(완료 시점 대기, 순차 실행, 제어의 역전)이 100% 일치함을 확인했습니다.
더 나아가 실제 구현 코드는 단순 람다 콜백의 리스크(메인 스레드 프리징, 취소 불가, GC 메모리 누수)를 해결하기 위해 `UniTask (WhenAll / CancellationTokenSource) + 커맨드 패턴 + FSM`이라는 상위 호환 아키텍처로 진화된 형태였음을 이론적으로 재확인했습니다.

C# vs Java 람다 정렬 비교 코드

C# Array.Sort
Array.Sort(words, (a, b) => a.Length - b.Length);
Java Arrays.sort
Arrays.sort(words, (a, b) -> a.length() - b.length());

6일차

3장 함수형 인터페이스 (SAM 인터페이스)

2026.09.16 20분 소요 (이론 + 실습) 완독

오늘 배운 핵심 개념

  • 함수형 인터페이스(Functional Interface)의 본질: 추상 메서드가 0개이거나 2개 이상이면 함수형 인터페이스가 아니며, 람다를 변수에 담기 위한 "추상 메서드 딱 1개짜리 규격 인터페이스(SAM - Single Abstract Method)"임.
  • C#의 Action, Func 델리게이트 역할을 자바에서는 이 함수형 인터페이스(Runnable, Supplier, Consumer, Function, Predicate)가 대신 수행함.
1줄 요약: 자바에서 람다를 담기 위한 그릇은 오직 "추상 메서드 1개짜리 인터페이스"뿐이다.

3장 @FunctionalInterface와 상속 규칙

2026.09.17 15분 소요 (이론 + 실습) 완독

오늘 배운 핵심 개념

  • 상속 규칙: 인터페이스를 상속받더라도 단일 추상 메서드를 제외한 추가적인 추상 메서드는 절대 담을 수 없음 (상속 후에도 최종 추상 메서드는 오직 1개여야 람다 자격 유지).

8일차

3장 타입 추론과 대상 타이핑(Target Typing), 연쇄 체이닝 극복

2026.09.18 1시간 30분 소요 (이론 + 실습) 완독

궁금했던 질문 (Questions)

  • 람다는 원래 타입이 없는가? 책의 사칙연산(Calculation, calculate, apply) 예제가 왜 그렇게 쓰였는가?
  • 메서드 호출 시 제네릭 문법(Collections.<String>emptyList())과 연쇄 호출(List.emptyList().add(...))에서 왜 컴파일 에러가 나는가?

핵심 개념 & 깨달음 (Takeaways)

  • 대상 타입(Target Type): 람다는 형태가 없는 액체 같아서, 대입되는 좌변 변수나 메서드 인자라는 "그릇(대상 타입)"을 보고 컴파일러가 역으로 타입을 알아맞힘.
  • 자바 람다의 정체 (인터페이스 객체): C#과 달리 자바는 함수를 직접 호출(add(2, 2))할 수 없어서, 인터페이스의 메서드 이름(apply)을 실행 방아쇠(접근자)로 사용하여 add.apply(2, 2) 형태로 호출함.
  • 연쇄 메서드 호출(Chaining)의 한계와 자바의 진화:
    • 기차놀이 체이닝(List.emptyList().add(...)) 시 타입 정보가 맨 앞칸까지 역방향으로 전달되지 못해 List<Object>로 평가되어 컴파일 실패함.
    • 자바 8에서도 이 한계를 완전히 해결하지 못해 타입 증인(.<String>)을 써야 했으나, 최신 자바(Java 9~21)에서는 List.of(), var, .toList() 등의 현대적 API 도입으로 이를 말끔히 해결함.
1줄 요약: 람다는 그릇(Target Type)을 보고 타입을 유추하며, 자바 8 체이닝의 한계는 현대 자바의 신규 컬렉션/스트림 API로 극복되었다!
