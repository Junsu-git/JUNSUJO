## 3. 경험 평가와 배운 점 (`#growth` — BEFORE / AFTER)

### 수행 전 (BEFORE: 직면한 과제와 한계)
- **초기 기획안(`ConsoleAuction`)에 대한 팀 내 장르 적합성 이견**: 처음에는 2D 탑뷰 서바이버 전투와 공간 조립(`생장판`), 비공개 경매(`뿌리 장터`)를 결합한 기획안을 제안했으나, 팀원으로부터 *"제한된 무기 운용과 경매·강화 구조라는 핵심 재미를 살리기에는 탑뷰 서바이버보다 다른 장르가 더 적합하다"*는 피드백이 제기되었습니다.
- **TCP 바이트 스트림의 패킷 경계 문제와 클라이언트 임의 상태 변경 위험**: 멀티플레이 환경을 직접 구축하면서, TCP 특성상 단일 `Receive` 호출에 패킷이 쪼개지거나 합쳐져 도착하는 스트림 경계 문제와 여러 비동기 송신이 겹칠 때 바이트가 섞이는 동시성 문제를 해결해야 했습니다.

### 수행 후 (AFTER: 달성한 성과 및 역량 성장)
- **공통 평가 기준 수립을 통한 장르 피벗(`비드 앤 디펜스`) 합의**: 자신의 초기안을 고집하는 대신 **핵심 재미, 구현 위험, 기대 효과, 팀원 관심도**라는 4가지 객관적 비교 기준을 세워 기존안과 대안을 비교했고, 모든 팀원이 납득할 수 있는 **멀티플레이 타워 디펜스 + 경매 전략(`비드 앤 디펜스`)**으로 방향을 발전시켰습니다.
- **3계층 서버 권한 아키텍처 및 길이 프리픽스(`PacketFraming`) 구현·검증**: `Unity Client` — `RootMarket.Protocol`(순수 C# 메시지 계약) — `RootMarket.Server`(.NET TCP 전용 서버)로 책임을 분리하고, 16바이트 헤더 기반 길이 프리픽스 프레이밍(`ReadExactlyAsync`), `SemaphoreSlim` 송신 직렬화, 서버 권한 `RoomSnapshot` 동기화를 구현해 로비 수직 슬라이스 단위/통합 테스트를 통과했습니다.

## 4. 개요 및 기획 의도 (`#overview`, `#mechanics`)

### 4.1 기획의 출발과 발전 과정 (`#overview`)
1. **1단계 — 초기 구상 (`Project Console Auction`)**:
   - 정해진 몬스터 수를 상대보다 먼저 처치하는 2D 탑뷰 서바이버 전투(60초)와 테트리미노 형태의 공간 조립 빌드크래프팅(`생장판`·`가지`·`접목편`, 10초), 그리고 라운드 사이 공유 아이템을 두고 경쟁하는 비공개 동시입찰(`뿌리 장터`)을 결합한 4인 FFA 게임으로 출발했습니다.
2. **2단계 — 팀 피드백 수용과 장르 재설계 (`비드 앤 디펜스 / RootMarket`)**:
   - 팀 회의 과정에서 "플레이어가 상대 전장과 재화 상태를 살피며 입찰 심리전을 벌이려면, 실시간 캐릭터 이동 조작에 시선이 묶이는 탑뷰 액션보다 **타워 디펜스** 형태가 핵심 재미와 훨씬 잘 맞는다"는 의견을 수용했습니다.
   - 이에 따라 **2~4인이 각자의 독립된 전장에서 몰려오는 웨이브를 방어하면서, 공용 경매로 고가치 무기·전리품을 낙찰받아 경쟁하는 멀티플레이 타워 디펜스**로 기획을 확립했습니다.

### 4.2 핵심 게임 규칙 (`#mechanics` — 캡스톤 과제 신청서 기준)
- **독립 전장 웨이브 방어와 `웨이브 붕괴(100마리)` 탈락 규칙**:
  - 각 플레이어는 동물 국가 세계관의 사령관이 되어 자신의 독립된 전장에서 몬스터 웨이브를 방어합니다.
  - 전장 내 **미처리 몬스터가 100마리 이상 누적되면 `웨이브 붕괴`로 즉시 탈락**하며, 마지막까지 생존한 플레이어가 최종 승리합니다.
- **기본 유닛 + 무기·애드온 장착 기반 성장**:
  - 플레이어는 기본 유닛을 배치하고, 상점 구매·합성·경매로 획득한 **1~5성 무기 및 애드온**을 장착시켜 유닛의 외형과 공격 방식, 사거리, 특수 효과를 변화시킵니다.
- **5웨이브 주기 공용 경매 (`참가자 수 + 2개` 전리품)**:
  - 매 **5웨이브마다** 고위험 몬스터 처치 후 **`참가자 수 + 2개`**의 전리품이 공용 경매장에 올라옵니다.
  - 플레이어들은 현재 자신의 방어선 위기도와 상대방의 보유 재화·전장 상태를 확인하며 제한 시간 내 입찰 경쟁을 벌이고, 서버가 입찰 가능 금액·낙찰·동률·환불을 판정합니다.

## 6. 멀티플레이 아키텍처 및 구현 구조 (`#architecture`)

### 6.1 3계층 책임 분리 및 서버 권한(Server-Authoritative) 데이터 흐름
클라이언트와 서버가 동일한 메시지 규약을 공유하면서도 UI/엔진 코드와 서버 판정 로직이 섞이지 않도록 3계층으로 분리했습니다.

```text
[Unity Client]
 View ↔ ViewModel (MVVM / R3)
   ↓
 LobbyService (유스케이스 요청: 방 생성, 목록 조회, 입장, 준비, 채팅)
   ↓
 LobbyNetworkClient (TCP 소켓 관리, RequestId 기반 비동기 요청-응답 대기)
   ⇅  (바이트 스트림 송수신)
[RootMarket.Protocol (Pure C# Shared Contract)]
 PacketFraming (16B Header + UTF-8 JSON Payload) / MessageType / DTOs
   ⇅
[RootMarket.Server (.NET Dedicated Server)]
 TcpLobbyServer & ClientConnection (세션 관리, ReadExactlyAsync, SemaphoreSlim 쓰기 직렬화)
   ↓
 Server LobbyService (정원 초과·중복 입장·방장 권한·채팅 길이 검증 → RoomSnapshot / ErrorResponse 반환)
```

- **서버 권한(Server-Authoritative) 상태 갱신**: 클라이언트가 '방 생성'이나 '입장', '준비' 버튼을 눌렀을 때 로컬 UI에서 임의로 성공 처리하지 않습니다. 반드시 서버가 정원 초과 여부, 중복 입장, 방장 권한 등을 재검증한 뒤 내려보낸 승인 상태(`RoomSnapshot`)를 수신한 시점에 화면 상태를 갱신하도록 구현했습니다.

### 6.2 길이 프리픽스 패킷 프레이밍 (`PacketFraming.cs`) 상세
TCP는 메시지 경계를 보장하지 않는 바이트 스트림이므로, 패킷 잘림(Partial Read)이나 뭉침(Sticky Packet) 현상을 안전하게 처리하기 위해 **16바이트 고정 헤더 기반의 길이 프리픽스 프레이밍**을 직접 구현했습니다.

```text
+-------------------+----------------------+------------------+----------------+--------------------+------------------------+
| BodyLength (4B)   | ProtocolVersion (2B) | MessageType (2B) | RequestId (4B) | PayloadLength (4B) | UTF-8 JSON Payload (N) |
+-------------------+----------------------+------------------+----------------+--------------------+------------------------+
```

1. **정확한 바이트 수 읽기 보장 (`ReadExactlyAsync`)**:
   - 먼저 `4바이트 BodyLength`를 읽은 뒤, 필요한 바이트가 모두 도착할 때까지 `ReadAsync`를 반복 호출하는 `ReadExactlyAsync`를 구현했습니다.
   - 만약 전체 프레임이 완성되기 전에 스트림에서 `0바이트`가 반환되면 원격 연결이 비정상 종료된 것으로 즉시 감지해 정리합니다.
2. **5단계 헤더 유효성 및 보안 검증**:
   - `BodyLength`가 최소 헤더 크기보다 작거나 최대 허용 크기(**64KB 상한**)를 초과하는지 검사하여 비정상 메모리 할당을 차단합니다.
   - `ProtocolVersion` 일치 여부, 정의된 `MessageType` 열거값 여부, 그리고 `PayloadLength`가 실제 남은 바이트 길이와 정확히 일치하는지 대조합니다.
   - 첫 바이트만 보내고 나머지 바이트를 지연시키는 연결(Slowloris류)을 막기 위해 **프레임 완료 타임아웃**을 적용했습니다.
3. **비동기 송신 직렬화 (`SemaphoreSlim`) 및 `RequestId` 매칭**:
   - 단일 TCP 연결에서 여러 비동기 송신(`Write`)이 동시에 호출될 때 서로 다른 패킷의 바이트가 뒤섞이지 않도록 **`SemaphoreSlim`으로 스트림 쓰기를 직렬화**했습니다.
   - 각 요청마다 고유 `RequestId`를 부여해 비동기 응답 대기열과 정확히 매칭되도록 구성했습니다.

## 7. 문제 해결 및 협업 의사결정 사례 (`#troubleshooting`)

### 사례 1. 팀원 피드백 수용과 객관적 평가 기준을 통한 장르 피벗 (`ConsoleAuction` → `비드 앤 디펜스`)
- **발생 배경**: 과거 다른 프로젝트(`퍼즐 앤 레이드`)에서 근거 없이 직관적인 인상만으로 피드백을 전달해 아쉬웠던 경험을 반성하며, 이번 캡스톤에서는 제가 먼저 제안한 초기 기획(`ConsoleAuction`: 2D 탑뷰 서바이버 + 공간 조립 + 경매)에 대해 팀원이 이견을 제시했을 때 감정이나 취향 싸움이 되지 않도록 접근했습니다.
- **해결 과정**:
  1. 먼저 팀원이 말한 핵심 의도("제한된 무기 운용과 공용 경매 심리전이라는 재미를 살리려면 플레이어가 전장 전체와 상대 상태를 볼 여유가 있어야 한다")를 정확히 정리했습니다.
  2. 기존안(탑뷰 서바이버)과 대안(멀티플레이 타워 디펜스)을 **① 핵심 재미 전달력, ② 멀티플레이 동기화 구현 위험, ③ 기대 효과, ④ 팀원들의 관심도**라는 4가지 공통 기준으로 나란히 비교했습니다.
  3. 비교 결과 타워 디펜스 구조가 경매 전략의 가시성과 서버 권한 판정 구조 모두에 유리하다는 결론에 도달했고, 팀원 전원의 합의로 `비드 앤 디펜스` 기획을 확정해 **캡스톤 디자인 대표 팀 선정**까지 이어졌습니다.

### 사례 2. TCP 부분 수신(Partial Read) 및 동시 송신 바이트 섞임 방지
- **발생 문제**: 소켓 통신 초기 구현 시 로컬 루프백 환경에서도 연속 메시지 전송이나 비동기 요청이 겹칠 때 JSON 역직렬화 오류가 발생할 위험이 있었습니다.
- **해결 과정**: `PacketFraming`을 별도 순수 C# 계층으로 분리하고, 조각난 바이트 스트림을 강제로 주입하는 단위 테스트와 `SemaphoreSlim` 동시 송신 테스트를 작성해 네트워크 하위 계층의 신뢰성을 먼저 검증한 뒤 Unity 로비 UI와 연결했습니다.

## 8. 구현 완료 범위 vs 향후 개발 로드맵 (`#showcase`)

> [!NOTE]
> 포트폴리오 및 면접에서는 **현재 실제 코드와 테스트로 검증 완료된 범위**와 **진행 중인 설계/구현 범위**를 투명하게 구분하여 제시합니다.

### ✅ 현재 구현 및 자동화 테스트 검증 완료 범위 (`2026.09` 기준)
- **`RootMarket.Protocol`**: 16바이트 헤더 길이 프리픽스 프레이밍(`PacketFraming.cs`), 64KB 크기 제한, 버전/타입/길이 검증, 요청·응답 DTO 및 JSON 직렬화
- **`RootMarket.Server`**: C# .NET TCP 소켓 서버(`TcpLobbyServer`, `ClientConnection`), `ReadExactlyAsync` 및 프레임 완료 타임아웃, `SemaphoreSlim` 송신 직렬화, 서버 권한 `LobbyService`(방 생성·목록 조회·공개/비공개 입장·퇴장·준비 상태·로비 채팅 검증 및 `RoomSnapshot` 반환)
- **`Unity Client (Lobby Vertical Slice)`**: `LobbyNetworkClient`, 클라이언트 `LobbyService`, MVVM(R3/UniTask) 기반 로비 UI 연동 및 단위/통합 테스트 완료

### 🚧 진행 중 및 향후 구현 범위 (캡스톤 로드맵)
- **실시간 인게임 전장 및 웨이브 방어 루프**: 기본 유닛 배치, 1~5성 무기·애드온 장착/합성, 미처리 몬스터 100마리 누적 시 `웨이브 붕괴` 탈락 판정
- **서버 권한 공용 경매 및 전투 상태 동기화**: 5웨이브 주기 `참가자 수 + 2개` 전리품 경매(입찰금 검증·낙찰·동률·환불 처리) 및 멀티플레이 전장 요약 상태 동기화

## 9. 배운 점과 아쉬운 점 / 회고 (`#takeaways`)

- **배운 점 (Learned)**:
  - **네트워크 기본기와 서버 권한 아키텍처 체득**: 고수준 엔진 네트워크 라이브러리에만 의존하지 않고 TCP 바이트 스트림의 프레이밍, 헤더 검증, 비동기 동시성 제어(`SemaphoreSlim`), 서버 권한 상태 동기화(`RoomSnapshot`)를 밑바닥부터 직접 구현하며 멀티플레이 시스템의 동작 원리를 깊이 이해했습니다.
  - **테스트 가능한 구조 분리**: 프로토콜과 서버 로직을 `UnityEngine` 의존성 없는 순수 C# 프로젝트로 분리한 덕분에, Unity 에디터를 켜지 않고도 패킷 파싱과 방 상태 규칙을 자동화 테스트로 빠르게 검증할 수 있었습니다. (이전 `Project Pharmacy`에서 아쉬웠던 자동화 회귀 테스트 부재를 실제로 극복한 지점입니다.)
  - **근거 기반의 팀 의사결정**: 내 초기 기획안이더라도 공통 평가 기준을 세워 팀원 피드백과 비교·검증하면 더 나은 게임 구조로 발전시킬 수 있다는 협업 원칙을 확립했습니다.
- **아쉬운 점 및 현재 집중 과제 (Lacked)**:
  - 현재 로비 수직 슬라이스와 네트워크 기반 구조를 탄탄히 다진 단계이므로, 캡스톤 최종 발표까지 웨이브 전투와 5웨이브 주기 공용 경매의 인게임 멀티플레이 루프를 완성도 높게 결합하는 데 집중하고 있습니다.
