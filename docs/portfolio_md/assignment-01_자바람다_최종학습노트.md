# 자바 람다 — 14개 단원 최종 학습 노트

## 1. 핵심 요약과 학습 기준

**람다 표현식과 메서드 참조는 코드를 짧게 줄이는 문법이 아니라, '동작을 값처럼 전달하고 책임을 분리하는 설계 도구'입니다.** 각 단원마다 대상 타입, 변수 캡처 규칙, 예외 처리 경계를 명확히 설명할 수 있도록 14개 단원 노트를 정리했습니다. Unity C#의 델리게이트·이벤트 구조와 비교할 수 있으나, 두 언어의 문법과 캡처 규칙은 분리해 다룹니다.

- **문서 상태**: 14개 단원 노트 작성 완료 / 2026-11-19 마감.
- **단원별 복습 구성**: 개념 정리 15분 → 예제 분석 30분 → 선택 기준 요약 15분 (총 약 60분 단위).
- **문서 구성**: 1–8단원 기존 핵심 기록(누적 300분 별도 보존)과 9–14단원 심화 노트·통합 예제.

## 3. 1–8단원 핵심 정리

### 01. 모던 자바로의 길

데이터 필터링이나 이벤트 처리에서 **동작 자체를 인자로 넘기면 반복 구조와 조건 로직을 분리**할 수 있습니다. 예를 들어 아이템 목록을 매번 다른 `for` 루프로 검사하는 대신, 판정 조건을 `Predicate`로 전달해 재사용성을 높입니다.

### 02. 모던 자바의 기능들

람다는 **동작의 표현**, 함수형 인터페이스는 **동작의 대상 타입**, 스트림은 **데이터 처리 파이프라인**입니다. 셋의 역할을 나누어 이해해야 API 시그니처에서 어떤 입력 타입과 반환 동작을 요구하는지 정확히 읽을 수 있습니다.

### 03. 함수형 프로그래밍의 배경

람다 대수에서 실무로 가져올 핵심은 **입출력을 명확히 하고 작은 동작을 조합하는 설계 관점**입니다. 람다 문법으로 코드를 짧게 줄이더라도 외부 상태를 직접 변경하면 순수 함수가 되지 않습니다.

### 04. 익명 클래스와 람다

익명 클래스는 **자기 자신의 `this`**를 갖지만, 람다의 `this`는 **둘러싼 외부 클래스의 인스턴스**를 가리킵니다. 따라서 익명 클래스를 람다로 단순히 치환하면 내부 참조 대상이 달라질 수 있으므로 스코프를 먼저 확인해야 합니다.

### 05. 람다 기본 문법

`(left, right) -> left + right` 형태에서 인자 목록, 화살표, 본문을 구분합니다. 한 줄 표현식은 값을 바로 반환하지만 블록 본문은 `return`이 필요합니다. 분기·로깅·예외 처리가 길어지면 이름 있는 메서드로 분리해 가독성을 지킵니다.

### 06. 함수형 인터페이스

표준 인터페이스는 역할에 따라 네 가지로 나뉩니다. `Supplier`(제공), `Consumer`(소비), `Function`(변환), `Predicate`(조건 판정)와 인자·반환값이 없는 `Runnable`입니다. C#의 `Func`·`Action`과 역할은 비슷하지만 제네릭 타입 소거와 캡처 방식은 다릅니다.

### 07. 어노테이션과 상속

`@FunctionalInterface`는 해당 인터페이스가 추상 메서드를 **오직 하나만** 가지는지 컴파일 시점에 검증합니다. `default` 메서드나 `static` 메서드, `Object` 클래스의 메서드를 재선언한 항목은 추상 메서드 개수 제한에 포함되지 않습니다.

### 08. 타입 추론과 대상 타이핑

람다의 타입은 대입받는 변수나 메서드 매개변수의 **대상 타입(Target Type)**으로 결정됩니다. `var f = x -> x + 1;`처럼 대상 인터페이스가 없으면 컴파일되지 않으며, 연쇄 호출에서 추론이 모호할 때는 명시적 타입 인자나 지역 변수로 타입을 고정해야 합니다.

위 문법 기준은 [Java 언어 명세의 람다·메서드 참조 규정](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.27)을 따릅니다.

## 4. 9–14단원 심화 노트

### 09. 메서드 참조 — 기존 동작에 이름 붙이기

**핵심 개념**: 람다가 다른 메서드 하나만 그대로 호출한다면 메서드 참조(`::`)로 의도를 더 선명하게 드러낼 수 있습니다. 정적 메서드, 특정 객체의 인스턴스 메서드, 타입의 인스턴스 메서드, 생성자 참조 네 가지를 구분합니다. [공식 메서드 참조 설명](https://docs.oracle.com/javase/tutorial/java/javaOO/methodreferences.html).

```java
Function<String, Integer> lengthA = text -> text.length();
Function<String, Integer> lengthB = String::length;
System.out.println(lengthB.apply("Mira"));
```

**예상 결과**: `4`. 메서드 참조 자체에 독자 타입이 있는 것은 아니며, 대상 `Function`의 입력·출력 규약과 일치할 때만 성립합니다.

**선택 기준**: 추가 변환 없이 기존 메서드를 그대로 위임하면 메서드 참조를 씁니다. 반대로 인자 순서를 바꾸거나 조건이 붙는다면 람다를 유지하는 편이 읽기 쉽습니다.

**학습 배분(약 60분)**: 참조 네 형태 비교 15분 · 기존 람다 변환 30분 · 가독성 판단 근거 정리 15분.

### 10. 변수 범위 — 지역 변수와 객체 상태 구분

**핵심 개념**: 람다가 외부 지역 변수를 캡처하려면 그 변수는 `final`이거나 사실상 `final`(effectively final)이어야 합니다. 참조 변수를 다시 대입하는 행위는 금지되지만, 참조가 가리키는 객체의 내부 필드를 수정하는 것은 문법상 허용됩니다(단, 멀티스레드 동시성 안전을 보장하지는 않습니다).

```java
int bonus = 3;
Supplier<Integer> score = () -> 10 + bonus;
System.out.println(score.get());
// bonus = 4; 를 추가하면 effectively final 조건이 깨져 컴파일 에러 발생
```

**예상 결과**: 재대입이 없으면 `13`을 출력하며, `bonus = 4;`를 추가하면 컴파일 단계에서 거부됩니다. (Java SE 규칙 기준 예상 결과)

**선택 기준**: 콜백이 외부 가변 상태를 오래 참조하면 버그 원인이 됩니다. 필요한 값만 불변 인자로 복사해 넘기거나, 상태 관리를 전담하는 클래스로 책임을 분리하는 편이 안전합니다.

**학습 배분(약 60분)**: 캡처 제약 확인 15분 · 재대입 vs 상태 변경 비교 30분 · 부수 효과 점검 15분.

### 11. 예외 처리 — 호출자가 복구 정책을 선택하게 하기

**핵심 개념**: `java.util.function`의 표준 인터페이스는 `checked exception`을 던지도록 선언되어 있지 않습니다. `IOException` 같은 검사 예외를 다루려면 예외를 선언한 전용 인터페이스를 정의하거나, 내부에서 안전하게 래핑·변환하는 정책을 세워야 합니다.

```java
@FunctionalInterface
interface CheckedSupplier<T> {
    T get() throws IOException;
}

static String readOrFallback(CheckedSupplier<String> source) {
    try { return source.get(); }
    catch (IOException failure) { return "fallback:" + failure.getMessage(); }
}
```

**예상 결과**: `IOException("offline")`이 발생하면 `"fallback:offline"`을 반환합니다. (실무에서는 장애 로깅이나 재시도 정책과 함께 설계)

**선택 기준**: 호출자가 실패 복구 방식을 직접 정해야 할 때는 `throws`를 드러낸 전용 인터페이스가 명확합니다. 스트림 파이프라인 내부에 긴 `try/catch`를 숨기면 정상 흐름과 예외 경로가 섞여 가독성이 떨어집니다.

**학습 배분(약 60분)**: 표준 인터페이스 한계 확인 15분 · 예외 전달 vs 내부 복구 비교 30분 · API 설계 기준 정리 15분.

### 12. 람다와 캡처 — 선언과 실행 시점 분리

**핵심 개념**: 람다를 생성·저장한 시점과 실제로 함수형 인터페이스 메서드를 호출해 실행하는 시점은 다릅니다. 특히 UI 버튼이나 게임 이벤트 콜백에 람다를 등록할 때는 캡처된 객체가 언제까지 메모리에 남는지(수명 주기)를 점검해야 합니다.

```java
static IntSupplier withBonus(int base) {
    return () -> base + 5;
}
IntSupplier reward = withBonus(10);
System.out.println(reward.getAsInt());
```

**예상 결과**: `15`. 메서드가 반환된 뒤에도 캡처된 `base` 값을 유지해 지연 실행 시 결과를 돌려줍니다. (실제 메모리 할당·캐싱 방식은 JVM 최적화에 따라 달라집니다.)

**선택 기준**: 큰 객체나 UI 컨트롤러를 캡처한 람다는 해제 시점을 놓치면 메모리 누수로 이어집니다. 이벤트 구독 해지 책임을 명시하고, 필요한 값만 최소한으로 캡처합니다.

**학습 배분(약 60분)**: 선언/실행 시점 도식화 15분 · 캡처 범위 점검 30분 · 참조 수명 정리 15분.

### 13. 바이트코드 — 컴파일 결과 확인 방법

**관찰 방법**: [LambdaReview.java](../../assignments/resources/lambda/LambdaReview.java)를 JDK 환경에서 컴파일한 뒤 `javap` 역어셈블러로 실제 생성 구조를 확인합니다.

```text

```

**핵심 확인 항목**: `-c` 옵션으로 바이트코드 명령을, `-p` 옵션으로 `private` 합성 메서드 생성 여부를 확인합니다. `javac`는 보통 `invokedynamic`을 통해 람다를 변환하지만, 실제 최적화와 객체 할당 횟수는 실행 시점 JVM과 측정 도구로 검증해야 합니다. [공식 javap 문서](https://docs.oracle.com/en/java/javase/21/docs/specs/man/javap.html).

**학습 배분(약 60분)**: `javap` 옵션 학습 15분 · 일반 메서드 vs 람다 바이트코드 구조 비교 30분 · 추정과 실측 구분 15분.

### 14. 통합 — 조건 필터링·정렬과 표현 선택

**예제 문제**: 가상의 플레이어 목록(`Mira Lv.12`, `Joon Lv.7`, `Ara Lv.20`) 중 **Lv.10 이상**만 골라 **레벨 내림차순 → 이름 오름차순**으로 정렬합니다.

```java
players.stream()
    .filter(player -> player.level >= 10)
    .sorted(Comparator.comparingInt((Player player) -> player.level)
        .reversed().thenComparing(player -> player.name))
    .collect(Collectors.toList());
```

**예상 결과**: 일반 `for`문 구현과 스트림·람다 구현 모두 `[Ara:20, Mira:12]`를 반환합니다. 두 결과가 어긋나면 통합 파일에서 `AssertionError`로 즉시 검증합니다.

**선택 기준**: 단순 조건 선별과 정렬 파이프라인은 스트림·람다가 한눈에 들어옵니다. 반면 분기별 로깅, 루프 조기 종료, 세밀한 예외 복구가 얽히면 이름 있는 메서드와 일반 반복문이 디버깅에 유리합니다.

**학습 배분(약 60분)**: 정렬 규칙 정의 15분 · 두 구현 코드 비교 30분 · 상황별 선택 기준 정리 15분.

## 6. 최종 회고

**람다 학습의 결론은 "코드를 짧게 쓰는 기술보다, 동작의 타입·수명·예외 경계를 설명하는 능력"입니다.** 대상 타입과 캡처 범위를 이해하고, 예외 복구 책임을 분리한 뒤에야 상황에 맞는 표현(람다 vs 메서드 참조 vs 일반 루프)을 고를 수 있습니다.

Unity C#의 `Action`/`Func` 콜백 설계에서도 같은 사고방식이 적용됩니다. 다만 언어별 캡처 방식과 가비지 컬렉션 수명 규칙이 다르므로, 성능 개선 여부는 반드시 프로파일러 실측으로 확인해야 합니다.

14개 단원의 개념 노트와 통합 예제 작성을 완료하고 과제를 마감합니다.
