## 1. 정리 결과와 적용 기준

**일반 메서드, 람다, 메서드 참조를 상황에 맞게 선택하는 기준을 14개 단원으로 정리했다.** 핵심은 코드를 짧게 만드는 것보다 대상 타입, 변수 캡처, 예외 경계를 설명할 수 있게 하는 데 있다. 게임 클라이언트의 콜백·이벤트를 읽을 때도 같은 질문을 적용할 수 있지만 Java와 C#의 언어 규칙은 구분한다.

## 3. 1–8단원 핵심 정리

### 01. 모던 자바로의 길

기존 기록에서는 자바 8 도입 배경을 짧게 살펴봤다. 같은 데이터 처리라도 동작을 인자로 전달하면 조건과 반복 구조를 분리할 수 있다. 예를 들어 아이템 목록을 매번 다른 루프로 검사하기보다 조건을 Predicate로 전달하는 방식으로 읽을 수 있다.

### 02. 모던 자바의 기능들

람다는 동작의 표현, 함수형 인터페이스는 그 동작의 대상 타입, 스트림은 데이터 처리 파이프라인이다. 셋을 하나의 기능으로 뭉뚱그리면 실행 시점과 반환 형태를 놓치기 쉽다. API를 볼 때 어떤 데이터를 받는지와 어떤 동작을 요구하는지를 나누어 읽는 것이 학습의 출발점이다.

### 03. 함수형 프로그래밍의 배경

기존 메모에서는 람다 대수와 리스프의 역사적 연결을 흥미롭게 봤다. 실무에 가져올 부분은 수학적 표현 자체보다 입력과 출력을 분명하게 하고 작은 동작을 조합하는 관점이다. 외부 상태를 변경하는 코드를 단순히 람다로 줄였다고 순수 함수가 되는 것은 아니다.

### 04. 익명 클래스와 람다

익명 클래스는 별도의 this를 가지며, 람다의 this는 둘러싼 문맥의 this를 따른다. 따라서 익명 클래스를 람다로 기계적으로 바꾸면 참조 대상이 달라질 수 있다. 이 차이는 언어 의미이며, 특정 컴파일러의 합성 메서드 이름이나 힙 할당 형태를 보장하는 규칙과는 구분한다.

### 05. 람다 기본 문법

`(left, right) -> left + right`에서 인자 목록, 화살표, 본문을 구분한다. 표현식 본문과 블록 본문은 return 사용 방식이 다르다. 분기·로깅·예외 처리가 길어지면 이름 있는 메서드로 분리하는 편이 역할을 설명하기 쉽다.

### 06. 함수형 인터페이스

Supplier는 값을 제공하고 Consumer는 값을 받아 처리하며 Function은 값을 변환하고 Predicate는 조건을 판정한다. Runnable은 인자와 반환값이 없는 작업을 표현한다. C#의 Func·Action과 역할은 비교할 수 있지만 타입 체계와 캡처 규칙까지 동일하다고 설명하지 않는다.

### 07. 어노테이션과 상속

`@FunctionalInterface`는 인터페이스가 함수형 인터페이스의 조건에 맞는지 컴파일 시점에 확인하게 한다. default·static 메서드가 있다는 이유만으로 자격을 잃지는 않는다. 추상 메서드의 상속과 Object 메서드 관련 규칙도 있어 단순히 메서드 선언 줄 수만 세어 판단하지 않는다.

### 08. 타입 추론과 대상 타이핑

람다는 대입 대상이나 메서드 인자가 요구하는 함수형 인터페이스를 바탕으로 해석된다. 최신 자바에서도 모든 연쇄 호출에서 기대 타입이 임의로 역전파되는 것은 아니다. 명시적 타입 인자나 지역 변수로 경계를 만들면 오류를 좁히기 쉽다. `var f = x -> x + 1;`은 대상 함수형 인터페이스가 없어 성립하지 않는 예다.

위 언어 규칙의 기준은 [Java 언어 명세의 람다·메서드 참조 규정](https://docs.oracle.com/javase/specs/jls/se21/html/jls-15.html#jls-15.27)이다. 기존 개인 메모의 비유와 언어가 보장하는 규칙을 나누어 정리했다.

## 4. 9–14단원 보완 노트

### 09. 메서드 참조 — 기존 동작에 이름 붙이기

**핵심 개념**: 람다가 기존 메서드 하나를 호출하기만 한다면 메서드 참조로 의도를 드러낼 수 있다. 정적 메서드, 특정 객체의 인스턴스 메서드, 타입의 인스턴스 메서드, 생성자 참조를 구분한다. 참조를 만드는 시점과 실제 호출 시점을 혼동하지 않는다. [공식 메서드 참조 설명](https://docs.oracle.com/javase/tutorial/java/javaOO/methodreferences.html).

```java
Function<String, Integer> lengthA = text -> text.length();
Function<String, Integer> lengthB = String::length;
System.out.println(lengthB.apply("Mira"));
```

**예상 결과**: `4`. String::length만으로 임의의 함수 타입이 생기는 것이 아니라 Function의 입력·출력 규약과 맞아야 한다.

**선택 기준**: 변환·분기 없이 한 메서드를 위임하면 참조를, 인자를 재배치하거나 조건을 추가하면 람다를 사용한다. 참조로 바꾼 뒤 오히려 어느 인자가 수신 객체인지 읽기 어려우면 원래 람다를 유지한다.

**약 60분 구성**: 참조 네 형태 비교 15분, 기존 람다를 참조로 변환 30분, 가독성 선택 근거 15분.

### 10. 변수 범위 — 지역 변수와 객체 상태 구분

**핵심 개념**: 람다가 사용하는 지역 변수는 final 또는 effectively final이어야 한다. 참조 변수를 재대입하는 것과 참조 대상 객체의 내용을 바꾸는 것은 다른 동작이다. 객체를 변경할 수 있다고 해서 동시성 안전까지 얻는 것은 아니다.

```java
int bonus = 3;
Supplier<Integer> score = () -> 10 + bonus;
System.out.println(score.get());
// bonus = 4; 를 추가하면 캡처되는 변수가 effectively final이 아니게 된다.
```

**예상 결과**: 재대입 없는 버전은 `13`. 주석의 재대입을 넣은 버전은 컴파일 실패가 예상된다. 이 두 결과는 현재 실행 결과가 아니라 비교할 규칙과 예상 결과다.

**선택 기준**: 콜백이 가변 상태를 오래 붙잡는다면 필요한 값을 불변 값으로 넘기거나 이름 있는 객체의 책임으로 분리한다. 값 캡처 제약을 피하려고 무조건 배열 한 칸을 사용하는 방식은 상태 변경의 이유를 숨길 수 있다.

**약 60분 구성**: 캡처 조건 15분, 재대입·객체 변경 사례 비교 30분, 부수 효과 설명 15분.

### 11. 예외 처리 — 호출자가 복구 정책을 선택하게 하기

**핵심 개념**: 표준 Supplier.get은 checked exception을 선언하지 않는다. IOException을 전달하려면 예외를 선언한 사용자 정의 인터페이스를 사용하거나, 내부에서 처리하거나, 명시적인 변환 정책을 둬야 한다.

```java
@FunctionalInterface
interface CheckedSupplier<T> {
    T get() throws IOException;
}

static String readOrFallback(CheckedSupplier<String> source) {
    try { return source.get(); }
    catch (IOException failure) { return "fallback:" + failure.getMessage(); }
}
```

**예상 결과**: IOException("offline")을 던지는 작업을 넘기면 `fallback:offline`. fallback은 이 학습 예제가 선택한 정책이며 모든 I/O 실패를 빈 값으로 숨기는 범용 권장은 아니다.

**선택 기준**: 실패 복구를 호출자가 결정해야 하면 경계를 드러낸 인터페이스가 낫다. 긴 try/catch를 스트림 안에 숨기면 실패 이유와 정상 결과를 구분하기 어려워진다.

**약 60분 구성**: 표준 인터페이스의 예외 선언 확인 15분, 실패 전달 두 방식 비교 30분, 복구 책임 정리 15분.

### 12. 람다와 캡처 — 선언과 실행을 나누어 읽기

**핵심 개념**: 람다를 저장한 시점과 함수형 인터페이스 메서드를 호출한 시점은 다르다. 캡처한 값이나 객체가 나중 실행에 어떤 영향을 주는지 따로 살펴야 한다.

```java
static IntSupplier withBonus(int base) {
    return () -> base + 5;
}
IntSupplier reward = withBonus(10);
System.out.println(reward.getAsInt());
```

**예상 결과**: `15`. 작업을 만드는 메서드가 반환된 뒤에도 만들어진 동작을 호출할 수 있다. 구체적인 객체 생성·캐시 전략은 JVM 구현과 최적화에 따라 달라질 수 있다.

**선택 기준**: UI 콜백에 큰 객체를 캡처하면 참조 수명을 검토한다. 이벤트 등록·해제 책임은 별도로 드러낸다. 이를 모든 언어에서 같은 방식으로 할당되는 ‘클로저 객체’로 단정하지 않는다.

**약 60분 구성**: 생성·호출 시점 도식화 15분, 값·객체 캡처 비교 30분, 수명과 부수 효과 정리 15분.

### 13. 바이트코드 — 문법 인상과 생성 결과 구별

**관찰 방법**: [통합 예제](../../assignments/resources/lambda/LambdaReview.java)를 JDK가 있는 환경에서 컴파일한 뒤 javap로 확인한다.

```text
javac -encoding UTF-8 LambdaReview.java
java LambdaReview
javap -c -p LambdaReview
```

**읽을 항목**: 일반 구현의 비교 메서드, 람다 호출 지점, 합성 메서드 유무, 캡처 인자가 전달되는 형태를 확인한다. javac의 일반적인 람다 변환에서 invokedynamic이 관찰될 수 있지만 특정 합성 메서드 이름·할당 횟수·성능 우위를 언어 규칙으로 확정하지 않는다.

`-c`는 바이트코드 명령, `-p`는 private을 포함한 멤버를 보여준다. [공식 javap 문서](https://docs.oracle.com/en/java/javase/21/docs/specs/man/javap.html).

**약 60분 구성**: 명령·옵션 15분, 일반 구현과 람다의 구조 비교 30분, 성능 추정과 실제 측정 구분 15분. 본 과제에서는 실제 디스어셈블 결과를 확보했다는 주장을 하지 않는다.

### 14. 통합 — 필터·정렬 결과와 선택 근거

**문제**: 플레이어 Mira Lv.12, Joon Lv.7, Ara Lv.20 중 Lv.10 이상만 고르고 레벨 내림차순, 같은 레벨이면 이름 오름차순으로 정렬한다. 이 값은 프로그래밍 예제의 가상 데이터다.

```java
players.stream()
    .filter(player -> player.level >= 10)
    .sorted(Comparator.comparingInt((Player player) -> player.level)
        .reversed().thenComparing(player -> player.name))
    .collect(Collectors.toList());
```

**예상 결과**: 일반 반복문 구현과 람다 구현 모두 `[Ara:20, Mira:12]`. 이름 동률 처리까지 조건에 포함해 정렬 결과가 일관되게 읽히도록 했다. 통합 파일은 두 결과가 다르면 AssertionError를 발생시키게 구성했다.

**선택 기준**: 데이터 선별·정렬 흐름이 짧으면 파이프라인이 읽기 쉽다. 분기별 로깅·조기 종료·예외 복구가 길면 이름 있는 메서드와 반복문을 선택할 수 있다. 람다가 항상 더 빠르거나 메모리를 적게 쓴다는 결론은 내리지 않는다.

**약 60분 구성**: 요구 조건 15분, 두 구현 비교 30분, AI 생성 코드 선택 이유 작성 15분.

## 5. 통합 예제와 예상 출력

현재 환경에서 JDK 실행 파일을 확보하지 못해 출력은 예상 결과로 제시한다. 노트 작성과 실행 검증을 구분한다.

완전한 import와 main을 포함한 [LambdaReview.java](../../assignments/resources/lambda/LambdaReview.java)를 함께 제공한다. Java 8 이상의 문법·라이브러리 범위로 작성했다. 실제 실행을 하지 않은 상태에서 아래 텍스트를 콘솔 캡처로 제시하지 않는다.

```text
method-reference=4
capture=13
exception=fallback:offline
closure=15
normal=[Ara:20, Mira:12]
lambda=[Ara:20, Mira:12]
```

## 6. 최종 회고와 마감

이번 노트의 결론은 **‘람다를 많이 쓰기’보다 ‘동작의 타입과 책임을 설명하기’가 우선**이라는 것이다. 대상 타입을 밝히고, 외부 상태 변경을 살피고, 예외 복구 책임을 분리한 뒤 가장 읽기 쉬운 표현을 선택한다.

Unity C#과 비교할 때도 콜백이라는 역할의 유사성과 언어별 캡처·이벤트 수명 규칙을 나누어 설명한다. 짧게 썼다는 이유만으로 GC 감소나 성능 개선을 확정하지 않는다.

14개 단원의 문서와 예제 작성을 완료한 범위로 과제를 마감한다. 과거 수행 날짜를 새로 만들지 않았으며, 실제 실행·학습 숙련도 인증은 이 문서의 완료 범위에 포함하지 않는다.
