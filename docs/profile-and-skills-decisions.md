# 이력과 보유 기술: 결정용 문서

사용자가 레이존 제외 후 진행을 요청하여 이력 확장안을 메인에 반영했다. 세부 정보가 없는 항목은 추후 수정으로 표시했다. 보유 기술의 5점 척도와 개인 점수는 아직 확정하지 않았다.

## 이번에 적용한 범위

- 최신 이력이 위로 오도록 유한대학교 → 사회복무요원 → CHRIST (Deemed to be University) → 서울디지텍고등학교 순으로 연결했다. 레이존은 제외했다.
- 학력과 복무를 하나의 흐름에서 읽을 수 있게 했으며, 소개 → 보유 기술 → 프로젝트 → 연락처 순서는 유지했다.
- SQLD·전공 대표·캡스톤 대표 팀 선정·모의 입사 경진대회 수상·누리살이 AI 기술상은 유한대학교의 관련 정보 카드로 묶었다. 데스크톱에서는 연표 오른쪽, 좁은 화면에서는 아래에 항상 표시한다. 두 카드의 제목과 상단 패딩은 같게 맞춘다. 펼침·접기 버튼과 상태에 따른 열 전환은 제거했다.
- 활동·수상 일자와 세부 명칭은 추후 수정으로 남겼고, 기술 점수는 넣지 않았다.

## 1. 이력은 얼마나 자세히 보여줄까?

**의견: 시간순 이력은 확장하되, 모든 활동을 같은 무게로 나열하지 않는 편을 추천한다.** 학력·인턴십·복무는 경로를 설명하는 연표에, 자격·대표 역할·수상은 대학 재학 시기의 활동이나 주요 성과로 구분하면 읽기 쉽다. 긴 설명을 펼쳐 놓기보다 각 항목을 한두 줄로 쓰고, 역할이나 결과의 근거가 있는 경우에만 링크를 붙인다.

학력·경력을 두 열로 분리하면 실제 개발 경력이 적은 현재는 한쪽이 비어 보일 수 있다. 하나의 연표에 `학력`, `인턴십`, `복무`, `활동`, `자격`, `수상` 라벨을 붙이는 방식을 우선 추천한다. 경력이 늘어나면 두 열을 검토해도 늦지 않다.

### 레이존 제외 결정

사용자는 해당 기간의 업무가 이사 지원과 IT 기업 컨퍼런스 부스 운영이었다고 설명하고 제외를 결정했다. 개발 경력으로 제시하지 않으며 현재 이력과 향후 추가 후보에서 제외한다. 과거 버전을 보존하기 위한 브랜치와 원본 아카이브는 수정하지 않는다.

### 메인에서 추천하는 정보량

1. 주요 경로: 유한대학교 → 복무 → CHRIST → 서울디지텍고등학교의 최신순.
2. 대학 활동: SQLD, 전공 대표, 캡스톤 대표 팀 선정을 유한대학교 관련 패널에 연결.
3. 주요 수상: 모의 입사 경진대회, GameAify AI 기술상도 같은 패널에 표시. 정확한 명칭·날짜는 추가 확인.

항목이 많아지면 메인에는 주요 경로와 성과를 요약하고 나머지는 '전체 이력' 펼침 영역에 둔다. 학업·인턴십·복무 기간이 겹치면 시작일만으로 인과관계를 만들지 않고 실제 기간 그대로 표시한다.

### 결정란

- 전체 이력 표현: **반영** — 최신순 연표 + 유한대학교 관련 정보 패널.
- 레이존: **제외 확정** — 현재 이력에 넣지 않음.
- 인도 대학: **사용자 제공 정보 반영** — 대학명·2019.06~2021.02·BBA 3년제·중퇴. 어학연수는 보조 정보로 표시.
- 자격·활동·수상 배치: **반영** — 유한대학교 오른쪽 관련 정보 패널. 일자가 없는 활동을 임의로 연도순 정렬하지 않음.
- 고교·대학·복무 기간: **반영**. 활동·자격·수상 날짜·직책·상명: **추후 수정**.

### 관련 이력 추가 방식

현재는 실제 관련 정보가 있는 유한대학교의 카드만 표시한다. 나중에 다른 학력·경력에도 자료가 생기면 기관명을 명시한 카드나 그룹으로 확장한다. 자료가 없는 항목에 빈 버튼·패널을 만들지 않는다. 접기·펼치기를 다시 넣기 전에 정보량과 위치 안정성을 검토한다. 최신 레이아웃 결정과 비교한 대안은 [소개 레이아웃 결정](intro-layout-decision.md)에 기록했다.

## 2. 보유 기술 5점 척도는 어떨까?

**의견: 현재는 점수보다 '어디까지 할 수 있는지 + 프로젝트 근거'를 먼저 보여주는 편을 추천한다.** C# 4/5나 Unity 5/5는 평가 기준이 없어 면접관에게 다른 의미로 읽힐 수 있다. 숫자를 붙이더라도 같은 기준으로 설명할 수 있어야 한다. 특히 기술·기획·협업을 서로 비교 가능한 하나의 점수처럼 보여주지 않는 편이 좋다.

| 방식 | 장점 | 한계 | 추천 |
| --- | --- | --- | --- |
| 할 수 있는 일 + 근거 링크 | 설명이 구체적이고 면접에서 방어하기 쉬움 | 점수처럼 즉시 비교되지는 않음 | 우선 추천 |
| 기준 없는 별 5개·진행률 | 한눈에 읽힘 | 자의적인 숙련도나 완성도로 오해하기 쉬움 | 비추천 |
| 행동 기준이 있는 5단계 | 시각적 비교와 설명을 함께 제공 | 기준과 근거를 관리해야 함 | 기준에 동의할 경우 선택 가능 |

### 5단계를 선택한다면 사용할 수 있는 기준 초안

이 표는 숙련도 등급의 공인 기준이 아니라 사이트 내부의 자기평가 초안이다. 아직 사용자에게 어떤 점수도 부여하지 않았다.

| 단계 | 설명 | 필요한 근거 예시 |
| --- | --- | --- |
| 1 | 기본 개념을 설명하고 예제를 따라 구현할 수 있음 | 학습 기록·작은 예제 |
| 2 | 자료와 도움을 받아 작은 기능을 구현할 수 있음 | 구현한 기능과 도움을 받은 범위 |
| 3 | 익숙한 범위의 기능을 스스로 구현하고 문제를 수정할 수 있음 | 직접 작성한 코드·문제 해결 기록 |
| 4 | 여러 대안을 비교해 구조를 개선하고 결과를 검증할 수 있음 | 선택 이유·개선 전후 근거·테스트 |
| 5 | 다른 사람이 재사용할 수 있게 정리하고 팀의 적용을 지원할 수 있음 | 문서·재사용 사례·리뷰·팀 적용 기록 |

5단계는 '전문가'나 '모든 상황에 능숙함'을 뜻하지 않는다. 도구와 기술 범위를 구체화해야 한다. 예를 들어 Unity 전체를 평가하는 것보다 UI, 데이터 연동, 상태 관리 등 경험한 범위를 밝히는 편이 정확하다.

선택 시 화면은 색 막대 5칸과 `3/5 · 익숙한 범위에서 독립 구현` 같은 텍스트를 함께 보여준다. 색만으로 상태를 전달하지 않고, 아래에 해당 판단을 뒷받침하는 프로젝트 링크를 둔다. 예시 숫자 3은 화면에 적용하거나 사용자 점수로 확정하지 않는다.

### 구성과 점수 입력란

아래 분류는 현재 화면을 바탕으로 한 검토용이다. 기술 구성 자체가 추후 수정 예정이므로 분류를 확정한 뒤 점수를 정한다.

| 분류 후보 | 실제 할 수 있는 일 | 점수 선택 시 값 | 근거 | 결정 |
| --- | --- | --- | --- | --- |
| Unity | 추후 수정 | 미정 | 약국·캡스톤 중 직접 담당 범위 | 미결정 |
| C# | 추후 수정 | 미정 | 직접 구현한 로직·문제 해결 | 미결정 |
| FSM·상태 관리 | 추후 수정 | 미정 | 캡스톤 구현 기록 | 미결정 |
| AI 연동 | 추후 수정 | 미정 | 누리살이 담당 기능 | 미결정 |
| 기획·데이터 분석 | 추후 수정 | 미정 | 플레이테스트·분석 과제 | 미결정 |

- 표시 방식: **미결정** — 추천: 할 수 있는 일 + 근거 링크 우선.
- 5점 척도를 사용할 경우 기준 채택 여부: **미결정**.
- 기술 분류와 각 점수: **미정**.

## 3. 결정 후 반영 순서

1. 위 결정란에 유지·제외·표시 방식을 적는다.
2. 이력의 날짜·직책·상명, 기술 분류와 설명을 확인한다.
3. 이 Markdown에 확정 내용을 반영한다.
4. 확정한 항목만 메인 페이지에 적용하고 모바일·테마·목차를 확인한다.
